# 当前报告：第三批表现、参数与整局体验

## 取消当前吊装（2026-10-22）

按用户确认加入主操作旁的“取消 · 放回来源”按钮与Esc快捷键。仅对本次从来货车或周转车抓起、尚未放置的箱子生效，可在闲置持货或XY移动中发起；下降、提升、放置后回原点和取消动作期间不可重复发起。

抓取时记录来源ID、车辆类型及索引、阶段、批次和箱ID；成功临停／落船时清除来源。取消经过返回来源、下降恢复原货物、安全提升三个阶段，镜头跟随吊具停在来源位置。周转车再次抓取建立新的来源，不会错误回到更早的货车。已正式落船的布局仍不可修改。

取消不调用正常落箱／临停计分，不触发工单、成长、接力或封顶，也不推进自动换批或结束。返回期间锁定新选位、重复取消及流程操作；即使箱子已经放回、吊具还在提升，流程锁仍保留。来源意外变化时拒绝覆盖，保留持货，不丢箱。

局内统计新增成功取消次数 `cancels` 及 `cancel-start`／`cancel-return` 事件；真实发生的抓取次数保留，不把取消当作新增临停、交付或放行。计分参数版本仍为phase3-v2。

验证：`check-cancel.cjs`覆盖四货车／双周转车、闲置与移动中取消、反复取消、阶段锁定、精确恢复、工单状态不变、末车不换批、来源占用不覆盖和取消后仍可正常交付；浏览器专项 `check-cancel-browser.cjs`覆盖桌面／触控、320px双按钮、来源标签、Esc、最后周转货取消不误结束，以及镜头与来源位置一致。原核心、工单与统计回归同时保持通过。

## 当前难度修订（phase3-v2，2026-10-22）

用户明确移除由原型自行增加的满列奖励，并要求两个阶段都必须依赖工单额外收益。当前规则：基础每半格50，上下同色每处半格邻接25，满列不加分；第一阶段2600，第二阶段3000，高分线仍8000。未改变各工单奖励系数、货量、镜头或回原点规则。

无工单单列严格上限＝36×50＋12条竖向半格栈×2处接触×25＝2400，低于两个阶段目标。即使全部满载且同色最优也不能通过；旧列超额分不能救当前列。记账中的 `completion` 字段仅保留零值兼容旧记录，不再有任何满列收益，配置与结算表现已移除该奖励。

关联处理：纯转色无法越过2400，因此首列不提供转色协议；边角专家在当前货池最多六次补齐，理论最多2400＋6×60＝2760，因此只持有它时第二列也不提供转色候选。协议仍留在其他可行组合中，没有删除工单或修改其效果。

复核采用 `balance-check` 的进度门槛分析，数据源为 `config.js`、`core.js`、`orders.js`、本报告、需求清单和 `balance-phase-three.cjs`。结论：**CONCERNS（满足强制工单收益目标，仍待真实试玩）**。

固定种子从20261021起，每种策略200局，所有策略使用真实三选一：

| 策略 | 通过／200 | 高分／200 | 总分中位数 |
|---|---:|---:|---:|
| 达标即交付 | 137 | 0 | 5767 |
| 普通持续装载 | 136 | 85 | 7703 |
| 单路线规划 | 200 | 149 | 10200 |
| 组合规划 | 200 | 199 | 9313 |

“普通”仍持有工单，只是不主动优化；无工单通关被理论上限严格排除。程序策略不能代表真人通关率，部分工单如边角专家余量较窄，仍应优先观察选卡后的实际体验。当前结果位于 `balance-phase-three-results.json`；旧版本结果归档为 `balance-phase-three-results-phase3-v1.json`。

检查：核心、工单240有序组合、统计专项及新增 `check-difficulty.cjs` 通过。原有纯规则组合测试中仍覆盖实际不提供的选卡组合，因此跨列采用显式门槛夹具，不再将“全部组合都可通关”作为断言。新难度专项覆盖200种子的候选限制、同色完美满载仍失败、旧列超额不抵扣以及可行转色仍保留。浏览器专项验证当前版本门槛、结算下载与放置后返回；完整操作和触控回归另见原检查脚本。

## 历史：第三批原型报告（phase3-v1，2026-10-21）

### 验证问题

在现有四车／双周转／两列工单循环中，玩家是否能读懂即时结算和永久放行的后果，普通交付是否允许不满载，高分是否需要继续装载和规划。

### 实现

- 共用 `config.js` 管理基础与工单参数、目标和表现时长，版本写入整局记录。箱体尺寸和投影保持现状；只在成功放置并提升后，让镜头与吊具一起返回原点。
- 结算浮层先显示基础、同色和满列，再显示每张工单的增量、成长和倍率前后值；卡片按顺序亮起，只对实际加分亮起。结果即刻入账，最多520ms的卡片表现与提升重叠；浮层2200ms自动移除，不增加确认步骤。
- 工单详情显示上次落船效果。顶部补足后续批次数；开场解释电／医。切批提示放行数；手动切列先展示永久放行余货与旧列封存的后果，可取消。周转结束提醒保留返回和放弃两条路径。
- 逐列记录前台作业时间、移动次数、周转取放、交付／装载率、放行、主动切列批次／时机。结算展示摘要并可导出含参数快照、种子、工单获得／排序和取放事件的JSON。选卡、详情、结算和后台不计时；记录只保存在当前局内存，重新开始前需自行导出。

# 第一批报告：四车分批与两列吊装（历史）

## 本轮实现

- 四车2×2来货，每列六批；双周转车独立成排，跨批跨列留货。
- 两列独立目标、提前切列永久放弃余货、不可撤销落箱、周转余货结束提醒和两档交付评价。

## 观测结果

# Prototype Report: 驾驶舱单列版本

## 当前版本：同色堆叠积分

## Hypothesis

固定驾驶舱俯视、单轴前后移动与手动升降能增强操作员体验，同时减少手机上的操作维度。

## Approach

以二维透视投影表现箱体、堆场、卡车和吊具。固定窗框，地面随驾驶舱移动，吊具靠升降缩放表现距离。卡车位于箱列起点，依次接红、蓝、黄三箱；暂不接入压箱、周转位和复杂规划。

## Result

浏览器已显示竖屏场景、固定窗框、单列箱子和四个按住操作按钮。完整流程通过 DOM/Canvas 模拟环境中的真实事件处理器与动画帧执行验证：抓取三个箱子、升降、返回卡车、自动换车并完成本班。真实手机的操作手感仍需试玩，不能据此判断趣味性。

## Metrics

- 3 箱、1 个装货位、后续 2 车预告。
- 只允许前后与升降两个维度，无左右移动。
- 控制区按钮至少 48 CSS px。
- 通过自动检查：3 箱完整交付、低位禁止移动、错色拒绝、撤销恢复、多指释放、指针取消。
- 未测真实手机帧率与触控延迟。

## Recommendation: PROCEED to playtest

让用户先判断俯视与缩放是否符合预期，目标箱是否能方便对齐，升降是否有足够距离感。根据试玩调整视野、速度和安全高度。通过后再讨论恢复压箱和周转位。

## Lessons Learned

吊具应围绕地面正下方的中心缩放；抓取前后保持吊具高度定义一致，避免载荷瞬间跳动。驾驶舱框架与堆场必须分别绘制，前者固定、后者随世界相对运动。

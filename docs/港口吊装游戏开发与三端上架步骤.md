# 港口吊装游戏开发与三端上架步骤

整理日期：2026年10月22日。

适用目标：个人开发者，将同一款原创游戏发布到微信小游戏、抖音小游戏和 TapTap 普通小游戏。本文的商业化规划暂按“免费游玩＋广告”安排，具体广告位置、奖励和首发范围仍需确认。TapTap 此处指点击即玩的普通小游戏，不是安卓 APK 或 TapTap 制造。

本文是后续执行路线，不表示全部步骤已完成，也不把此前建议视为已经批准的设计决定。勾选框用于后续验收；没有核实的账号、资质与后台状态不默认完成。

## 一、目前开发到哪里了

当前阶段：**核心玩法网页原型已实现，等待真人试玩确认；尚未完成 Cocos 正式版与三端平台接入。**

| 项目 | 当前状态 |
|---|---|
| 原型版本 | phase3-v2，2026年10月22日；已追加取消当前持货 |
| 装载循环 | 四车分批、双周转车、两列推进、放行与结束流程已实现 |
| 构筑与计分 | 两家货主、16张工单、三选一、排序、成长、倍率与跨列联动已实现 |
| 表现与记录 | 逐项结算、工单详情、结果摘要和本局记录导出已实现 |
| 程序验证 | 当前报告记录规则、模拟和浏览器检查通过；本次整理未重新运行测试 |
| 人工验收 | 真实手机触感、误触、阅读负担、晕动、性能和真人数值平衡待确认 |
| 正式工程 | Cocos 正式工程、三端构建及平台功能尚未完成 |
| 开发者与资质 | 三家账号、软著、备案、广告与结算开通状态待逐项核实 |

当前试玩参数为列门槛2600／3000、高分线8000；满列额外奖励已移除，无工单单阶段最高2400，仍为实验配置。已吊起未放置的箱子可取消并回本次来源，已落船布局仍不可撤销。模拟策略结果不能视为真人通关率或玩法已经验收。

进度依据：[当前原型说明](../prototypes/harbor-operator/README.md)、[当前原型报告](../prototypes/harbor-operator/REPORT.md)、[三批修改与测试清单](harbor-prototype-plan-2026-10-21.md)。

历史快照仍保留“双车、固定货量必须装完”等旧规则。正式迁移前，应以最新用户确认及[10月21至22日归档](harbor-session-2026-10-22.md)、[当前规划](harbor-future-plan.md)为基础统一规则；未决定的设计另列，不直接照搬历史文档。

## 二、12步执行计划

| 步骤 | 具体工作 | 完成标准 | 分工 |
|---|---|---|---|
| 1. 验收当前原型 | 体验取货、临停、放行、切列、选工单、排序、成功与失败；记录误触、看不懂和等待过长的位置 | 主要流程完成试玩，关键问题修复，确认核心循环值得继续制作 | 用户试玩与决定，Codex修复与记录 |
| 2. 确定首发范围 | 明确首发模式、关卡量、工单池、教程、存档及广告用途；逐项决定每日挑战、特殊货物等是否首发；统一最新规则文档 | 形成首发必需清单、后续更新清单和待定事项 | 共同确认，Codex整理 |
| 3. 注册三家开发者账号 | 本人认证，创建小游戏，核实实际游戏类目、个人发布权限、广告开通和收款要求 | 获得三个AppID，确认个人主体能走通各端准入路径 | 用户完成实名，Codex协助整理 |
| 4. 确定名称与权属材料 | 确定正式名称，整理代码、美术、字体、音效授权；按平台要求准备软著及其他材料 | 名称与主体信息一致，权属可证明，所需申请已按计划启动 | Codex准备技术材料，用户核对申报 |
| 5. 建立Cocos三端小样 | 用占位资源实现选箱、吊起、放下、计分及基础存档；分别构建微信、抖音和TapTap包，在手机运行；条件允许时验证广告测试接口 | 三端均完成一次吊装，关键接口路径可行，再锁定引擎和插件版本 | Codex负责工程，用户配合设备与后台操作 |
| 6. 迁移完整核心玩法 | 迁移四车、周转车、两列、货单生成、全部工单、结算及失败流程，使用已有规则测试校对 | 与已确认原型规则一致，无重复计分、丢箱和流程卡死 | Codex实施与验证，用户体验确认 |
| 7. 完成首发内容与表现 | 制作正式场景、界面、教程、音效、动画和首发关卡，改善箱位、颜色与货主识别 | 新玩家不靠口头指导也能完成首局并理解主要得分来源 | Codex制作与接入，用户确认方向与体验 |
| 8. 接入平台功能 | 分别接入广告、存档、前后台恢复，以及平台要求的登录、实名／防沉迷能力；完成隐私设置与必要的同意流程 | 广告关闭、失败、无填充时流程正常；重进后恢复应保留的进度；隐私文案与实际数据处理一致 | Codex实现，用户完成必要签约和结算认证 |
| 9. 提交备案／核准 | 使用与上线内容一致的包体和介绍，在三家后台按要求提交资质、小游戏备案及ICP核准／备案接入 | 三端后台均满足发布前置条件；已有备案按提示办理接入或复用，避免盲目重复申请 | Codex整理材料，用户完成身份及短信核验 |
| 10. 小范围真机测试 | 覆盖Android、iPhone、不同屏幕及较低性能设备；验证弱网、断网、切后台、广告返回、存档和完整通关 | 严重问题清零，计分、核心流程和恢复机制稳定 | 用户及受邀玩家试玩，Codex定位与修复 |
| 11. 准备商店材料并提审 | 制作图标、截图、简介、操作说明、适龄信息、客服方式及隐私政策；上传版本，处理审核反馈 | 三端分别审核通过，包体与截图、介绍和申报内容一致 | Codex准备与修复，用户核对和完成必须本人执行的操作 |
| 12. 分批发布与首轮维护 | 先发布一端观察真实问题，再发布另外两端；保留发布包、版本记录和紧急修复方案 | 三端正常游玩，广告与结算状态可核对，首轮问题处理完成 | 用户确认发布安排，Codex协助执行、排查与更新 |

## 三、哪些可以同时做

1. **立即并行：第1—2步与第3—4步。** 试玩、确定范围的同时办理账号准入与准备权属材料；名称未确定时，先不提交绑定名称的正式材料。
2. **先验证再全面迁移：第5步先于第6—7步。** 避免正式美术与界面制作完成后才发现某端无法正常运行。Cocos是建议路线，先用三端小样确认后再锁定具体版本。
3. **后期开发与审核等待交叉：第9步可与第7—10步适当交叉。** 以平台开放的入口和所需稳定包体为前提；提交后的重大内容变更要先判断是否需重新审核。
4. **第10—11步可交叉准备。** 测试时同步整理截图、文案和操作说明；正式提审前确保材料对应最终包体。
5. **三端分别过审、分批发布。** 发布顺序根据实际审核、稳定性和广告权限决定，不强求同一天上线。

不在当前阶段承诺具体上线日期。开发进度还受首发范围、用户验收、真机问题和平台审核影响；审核等待时间应单独计入计划。

## 四、三家平台各自要准备什么

| 平台 | 当前执行重点 |
|---|---|
| 微信小游戏 | 注册个人小游戏账号；先在后台核实本游戏类目与个人主体权限；按实际流程完成资质、小游戏备案、小程序备案及版本审核；单独核实流量主开通与个人收款要求 |
| 抖音小游戏 | 个人认证、AppID、软著等所需资质、基础信息与版本审核；无版号路径先完成小游戏备案，再办理ICP核准；广告签约和结算资料另行完成 |
| TapTap普通小游戏 | 完成个人认证开发者入驻、AppID及包体；按前置备案流程提交权属、内容介绍和负责人信息；完成版本审核及广告接入；个人主体负责人应为本人 |

微信官方文档本次未能直接读取，具体类目、材料、广告门槛应在第3步通过实际后台核实，不把第三方文章中的数字直接作为执行要求。

普通入驻与特别合作应分别看待。签独家发行、首发或带排他条件的扶持协议前，应核对是否影响另外两端发布。个人准入、广告接入和内购权限也是不同事项；如果后续增加付费解锁、付费去广告或道具购买，应重新核实主体、版号及支付能力要求。

## 五、工程安排

建议维护一套核心规则，通过平台适配层分别处理广告、存档、登录、分享、振动和前后台事件，避免在玩法代码中散布三套平台判断。

现有计分、工单和关卡逻辑可评估后复用；依赖HTML/CSS和DOM的按钮、弹窗及交互需迁移为小游戏兼容实现。浏览器原型继续用于验证玩法，Cocos工程承接正式制作与平台构建。

三端小样优先跑通微信，再验证TapTap转换流程，同时完成抖音构建。TapTap官方Cocos插件使用微信小游戏构建产物进行转换，当前文档要求Creator 3.8.x及以上；具体引擎小版本和插件需以实际构建、真机结果锁定。

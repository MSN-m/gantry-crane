本表依据截至2026-10-22的[讨论归档](harbor-session-2026-10-22.md)与2026-10-23关于丰富度、调度、消耗道具的对话整理。条目的“本次登记”是整理日期，不冒充原始提出日期。**本次只整理资料，不加入任何新玩法。**

## 1. 文档分工与维护约定

| 资料 | 负责什么 |
|---|---|
| 本表 | 想法分类、稳定编号、来源、当前决定、未决问题与变更历史；未来候选的维护主表 |
| [未来规划](harbor-future-plan.md) | 当前游戏方向、已确认规则、未来范围摘要；候选细节引用本表 |
| [工单管理表](harbor-work-order-registry.md) | 已接入工单的ID、效果、参数、投放限制、测试与修改历史 |
| [实施与测试清单](harbor-prototype-plan-2026-10-21.md) | 已获授权实施的内容、执行批次与人工验收 |
| 日期讨论归档 | 保存当时的过程和上下文，不随新决定改写旧结论；增加指向最新记录的提示即可 |

后续只要相关沟通产生**新想法、明确确认／否定／暂缓，或实质规则变化**，就在该轮结束前同步本表，不等到“一键归档”才记录。单纯解释既有规则且没有新结论时，不制造一条新决策。

维护顺序：

1. 先查已有ID，优先补充同一条；不因改名、换包装或重复讨论另建重复记录。
2. 记录提出者与日期、用户具体认可的范围、仍未确定的细节。用户认可大方向，不自动认可下面每个例子、数值或实现。
3. 用户明确同意的部分与Codex建议分开写；没有决定的部分保留待定，不代替用户拍板。
4. 变更状态时保留旧状态及理由，新增历史记录；不要删除被否定、封存或被替代的想法。
5. 细化为设计或实际进入开发时，补充设计／实现／测试链接。**记录、方向认可、获准开发和完成验收是不同事情。**
6. 若改变当前已执行规则，同时更新未来规划、相关规则文档和测试清单；涉及具体工单时同步工单管理表。不要改写旧日期归档以伪造当时已确认。
7. 未确认想法不自动进入原型；只有讨论、整理要求时，不据此开工。

同一功能可有多个使用渠道，但只保留一条功能记录。例如额外周转车记为 `CAP-001`，消耗道具与广告都引用它；批准其中一种渠道不代表其他渠道也批准。

## 2. 状态含义

| 状态 | 含义 |
|---|---|
| 候选待确认 | 提出过，但用户未明确接受具体方案 |
| 方向认可·细节待定 | 已接受方向或希望以后加入；具体规则、参数、获取方式与实施时机仍待定 |
| 已确认·待实施 | 具体范围已确定；仍须区分是否已授权立即开发 |
| 实施中 | 已获授权并开始；附任务或实现记录 |
| 已实现·待验收 | 已接入并有检查依据，但人工体验尚未通过 |
| 已验收 | 有用户或相应测试负责人的明确验收记录，不以程序检查代替 |
| 暂缓／后置 | 明确以后再讨论或本轮不做，不等于永久否定 |
| 封存 | 已决定先停下该思路，需明确重新开启后再推进 |
| 本轮不采用 | 明确排除在当前范围之外，不擅自扩大为永久禁止 |
| 已否定 | 用户不认可该方案；重提时必须指出是重新讨论而非既定规划 |
| 被替代 | 由另一条路线承接，记录替代关系，不再当成并行待开发系统 |

下列条目均未因本次整理获得开发授权，未设置虚构的优先级或排期。

#### ECO-001：命名演进与经济初稿（2026-10-23，最新决定覆盖历史候选）

- 用户明确边界：局内资源与未来可能采用的钱／金币区分，寻找贴近现实作业的概念；本轮先讨论名称及含义。
- Codex候选“作业额度”：把额外协调、人手和设备服务的成本抽象为可消耗额度，覆盖面较宽；推荐优先讨论，但未获用户选定。
- Codex候选“调度额度”：强调安排车辆、调用周转等协调资源；用于额外工单的解释较窄，名称不代表恢复独立调度权限系统。
- Codex候选“作业凭证”：完成作业获得凭证，用于兑换局内支持；更像兑换资源，须与已有工单和消耗道具的票据表现区分。
- 上述是游戏资源包装方案，不将其表述为现实港口通行的正式货币。没有确认发放、结算、清零、兑换、数值、图标或界面方案。

后续反馈：用户认为“作业额度”等解释字多、逻辑绕，要求类似“工分”的短词。优先采用直观、少解释的命名方向；“工分”为用户提出的候选，尚未明确最终选定。Codex当前推荐收敛为“工分”，备选“作业点”“贡献点”；此前额度／凭证方案保留为历史候选，不继续作为当前推荐。收入、用途与兑换规则仍未确认。

最新决定：用户确认“先叫工分”，当前暂定名为**工分**，覆盖上段未定名状态；不再并列推进其他命名。只是名称确认，不代表发放、兑换、价格、跨阶段保留或商店已定案。

最新用途决定：用户明确工分第一个兑换物为**合约**（原称工单），并提出经济初稿：开局5工分、每份合约3工分、刷新列表2工分。用户用“比如”举例，具体数值记录为讨论参数，未作平衡定案；货币单位统一写工分，不写元／金币。

| 项目 | 讨论参数／边界 | 来源与状态 |
|---|---|---|
| 开局持有 | 5工分 | 用户示例，暂未实施 |
| 兑换一份合约 | 3工分 | 用户示例，暂未实施 |
| 刷新合约候选列表 | 2工分 | 用户示例，刷新范围与重抽规则待定 |
| 直接兑换一次 | 花3，剩2 | 数学推演，不代表余额跨阶段保留已确认 |
| 先刷新一次再兑换 | 花2＋3，剩0 | 数学推演，不代表刷新次数或阶段补充规则已确认 |

Codex本轮讨论建议：用工分兑换替代现有免费三选一，先沿用三项候选的列表；这两点仍需用户确认，不直接改变原型。下一阶段如何补充工分也未决定，须结合已有合约跨阶段保留与当前门槛检查可达性，不能直接断言余额为零必死或默认赠送补贴。

归档停点：**是否以工分兑换替代原有每阶段免费三选一，尚待用户回答。** 用户只要求将问题及上下文归档，没有在归档请求中确认替代。恢复讨论先接这个问题，再逐项讨论收入与其他规则。完整关联见[2026-10-23归档第4—6节](harbor-session-2026-10-23.md)。

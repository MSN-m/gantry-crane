## 当前玩家文案：简写与术语统一（2026-10-26，已实施）

过关积分统一称“绩效”，兑换资源仍为“工分”；放到船上的动作统一称“装船”，周转不触发。合约主描述使用“补齐一层／箱位装满”，左右仅保留在选位操作及必要详情。用户确认封顶仍结算该箱位所有箱子的基础与同色绩效，未扩展为重复其他合约奖励。

| 合约 | 主描述 |
|---|---|
| 追加报酬 | 每装一箱，绩效额外＋25。 |
| 长期客户·电 | 每装一只电力箱，奖励20绩效；此奖励每次提高10。 |
| 长短接力 | 长短箱交替装船，奖励每次增加10绩效。 |
| 边角专家 | 以短箱补齐一层，绩效额外＋60。 |
| 封顶交付 | 箱位装满，该箱位所有箱子的基础绩效和同色绩效再结算一次。 |
| 转色协议·红蓝 | 红、蓝箱视为同色。 |
| 优先提货·电 | 每装一箱，整船每只顶部无遮挡的电力箱，绩效额外＋20。 |
| 加急奖金 | 本次绩效×1.5。 |
| 复核奖励 | 左侧合约的本次绩效，再结算一次。 |

医疗及其他双色版本对应替换对象名称。首箱不奖励／同尺寸接力重置、封顶仅一次、长箱遮挡判定、转色不传递、复核不重复成长等限制移入 `orders.js` 的 `details` 并在合约详情展示。市场展示短描述，五张卡使用紧凑状态提示；面板、目标提示、预览、结算明细和结果统一称绩效。数值、条件与结算顺序不变，内部字段保留兼容。下方早期“分／得分／落船”表述为历史规则说明，以本节当前文案为准。

## 合约评估维度候选（2026-10-26，待讨论）

| 维度 | 衡量什么 | 当前合约示例与边界 |

## 所有工单共用的规则

1. 货主本身没有能力。电、医分别是电力设备公司与医疗用品公司的简称，两家都可以有四色及长短箱。
2. 每阶段开始前获得一次三选一，选一张后开始。已有工单及成长跨阶段保留，当前两阶段原型最多正常获得两张。
3. 已持有的同ID工单不再提供；没有重复获取、升级、替换、购买或额外槽位系统。同机制不同ID不等于同一张卡。
4. 同一次三选一提供三个不同机制。例如两张不同货主的长期客户不会同时占据两个候选位，但第二阶段仍可能获得另一货主版本。
5. 正式落船只产生一次落箱事件；抓取、移动、周转车临停与取回都不计分、不成长、不推进接力或封顶。
   取消未放置的持货、送回本次来源同样不触发这些效果；正式落船后仍不能撤销。
6. 先算本次基础分与上下同色分，再从左到右结算工单。满列没有额外奖励。玩家可在允许操作时调整工单顺序，已得历史分数不重算。
7. 额外计分不重新执行整条结算，不增加交付箱数，不重复成长或创建新的封顶标记。
8. 新工单从取得后的落箱开始生效，不补发以前的收益或成长。旧列分数封存，布局可参与适用的新触发，新收益记到当前列。
9. 每次乘法当场四舍五入到整数；后面的倍率继续作用于前一步已取整的结果。
10. 工单卡可点开查看完整规则、当前状态及上次落船效果；箱子不添加工单专属标记。

| 参数位置 | `config.orders.priority = 20` |
| 跨阶段状态 | 没有成长值；每次重查当前列及封存列的可提货箱 |
| 顺序与复核 | 排在倍率之前可被放大；复核可重复本次算出的加分 |
| 失效边界 | 被遮挡的箱子停止后续贡献，已获得的历史分不扣回；不要求新箱属于指定货主 |
| 验证重点 | 别家落箱也触发；长箱半边被压不计；旧列贡献记入新列 |

例：放置后整船有2只电力箱无遮挡，本次额外＋40；放医疗箱也能得到这40分。

### 2. 长期客户（电／医各一张）

| 字段 | 内容 |
|---|---|
| ID与对象 | `client-power`：电力设备公司；`client-medical`：医疗用品公司 |
| 玩家说明要点 | 正式交付指定货主箱时，先按当前奖励发分，再提高后续奖励 |
| 触发条件 | 本次落船箱的货主匹配，长短箱成长次数相同，都是一次 |
| 参数位置 | `config.orders.clientStart = 20`；`clientGrowth = 5` |
| 局内状态 | `state.reward`：下一次匹配交付使用的奖励，跨阶段保留 |
| 顺序与复核 | 复核重复本次正常触发时的奖励值，不用成长后的金额，不再成长 |
| 不触发情况 | 交付另一家货主、临停与取回均不成长；其他货主不会将已有成长清零 |
| 验证重点 | 正常匹配只成长一次，复核不重复成长，切阶段后奖励保留 |

例：第一次匹配给20，之后奖励变25；同次被复核再给20，奖励仍只变为25。

### 3. 长短接力

| 字段 | 内容 |
|---|---|
| ID | `relay` |
| 玩家说明要点 | 按真实落船顺序长短交替，奖励逐档递增；同尺寸重置 |
| 参数位置 | `config.orders.relayStep = 10` |
| 局内状态 | `state.lastSize`：上次正式落船尺寸；`state.streak`：当前连续交替次数 |
| 初始与重置 | 新取得后首箱奖励0；相同尺寸本次0、档位归零，下一次成功交替从10开始 |
| 跨阶段 | 切批、切阶段和周转操作不打断已有状态 |
| 顺序与复核 | 复核重复当前档加分，不推进接力、不更新上次尺寸 |
| 验证重点 | 连续交替、同尺寸重置、跨阶段延续，取得前的交付不补进状态 |

例：长→短→长→长→短，对应接力奖励0、10、20、0、10。

### 4. 边角专家

| 字段 | 内容 |
|---|---|
| ID | `corner` |
| 玩家说明要点 | 短箱落下，使同一完整箱位左右高度相同，奖励60分 |
| 参数位置 | `config.orders.corner = 60` |
| 触发条件 | 本次必须是短箱，放置后左右高度相等；长箱自然齐平不触发 |
| 局内状态 | 无成长、无一次性标记；后续合法的短箱补齐可以继续触发 |
| 顺序与复核 | 可被复核；如同次也封顶，两个工单分别处理，不增加交付次数 |
| 获取限制 | 可以作为首张；仅持有它时，第二阶段不提供转色协议 |
| 验证重点 | 补齐才计，制造高低差不计，长箱不计，复核重复固定奖励 |

例：左右原来为2／1层，短箱落到右侧变2／2，本次额外＋60。

### 5. 封顶交付

| 字段 | 内容 |
|---|---|
| ID | `cap` |
| 玩家说明要点 | 完整箱位左右首次都达到三层，将其中基础分与同色分额外结算一次 |
| 奖励公式 | 箱位内占用半格数×50＋当前有效颜色判定下的上下邻接数×25 |
| 参数位置 | 没有独立固定奖励；引用 `config.basePerHalf`、`samePerHalf` 与当前三层容量规则 |
| 局内状态 | `state.marks` 保存“阶段：箱位”标记，同阶段同箱位只正常触发一次 |
| 跨阶段 | 标记保留且区分阶段；新阶段同位置是新的箱位，旧列已封顶位置不会在后续落箱时补发 |
| 顺序与复核 | 可以复核本次封顶加分，但不新增标记、不重新触发全部工单；额外金额不包括其他工单分 |
| 与转色关系 | 本次追加金额使用当前已持有的全部转色协议；不改写这个箱位以前的历史得分 |
| 验证重点 | 左右都三层、每位一次、复核不制造新事件、转色只影响新计算 |

例：一个箱位堆了3只同色长箱，其基础300、上下同色100，封顶额外＋400。这是工单效果，和已移除的“整列装满＋200”无关。

### 6. 转色协议（六张）

| ID | 独立配对 |
|---|---|
| `convert-red-blue` | 红↔蓝 |
| `convert-red-yellow` | 红↔黄 |
| `convert-red-green` | 红↔绿 |
| `convert-blue-yellow` | 蓝↔黄 |
| `convert-blue-green` | 蓝↔绿 |
| `convert-yellow-green` | 黄↔绿 |

| 字段 | 六张共用的规则 |
|---|---|
| 玩家说明要点 | 固定配对两色计分时互视为同色，实际箱色不变，多张协议不传递 |
| 生效时机 | 取得后即作为颜色判定规则参与新落箱同色分与封顶追加计算，不依赖卡片位置 |
| 参数位置 | 配对记录在 `orders.js` 的 `pair`；无独立加分值，同色分引用 `config.samePerHalf = 25` |
| 局内状态 | 无成长；配对固定，玩家不再另选颜色 |
| 顺序与复核 | 被动规则不因移到后方而失效；复核不能重复颜色互认，也不凭空制造加分 |
| 获取限制 | 当前只在第二阶段满足候选条件时出现；已有边角专家时不提供 |
| 历史边界 | 不重算取得前的同色分，也不改变已封存的历史分数 |
| 验证重点 | 六个固定ID、双向互认、不传递、无追溯；复核该卡时显示无可重复效果 |

例：同时有红蓝、蓝绿协议时，红蓝可互认、蓝绿可互认，但红绿仍不互认。正常两阶段原型首张不提供转色，因此双协议属于规则测试覆盖的组合，不是当前正常选卡可获得的路线。

### 7. 追加报酬

| 字段 | 内容 |
|---|---|
| ID | `flat` |
| 玩家说明要点 | 每次正式落船固定＋25，长短相同 |
| 参数位置 | `config.orders.flat = 25` |
| 局内状态 | 无成长、无一次性标记 |
| 顺序与复核 | 放在倍率前后会改变结果；复核可再给25 |
| 验证重点 | 每箱一次、长短相同、临停不触发、复核不增加交付数 |

例：长箱无同色奖励，先追加再加急＝(100＋25)×1.5取整＝188；先加急再追加＝100×1.5＋25＝175。

### 8. 加急奖金

| 字段 | 内容 |
|---|---|
| ID | `rush` |
| 玩家说明要点 | 轮到此卡时，把本次已累计得分×1.5，立即兑现 |
| 参数位置 | `config.orders.rush = 1.5` |
| 局内状态 | 无成长、无次数消耗 |
| 顺序与复核 | 只乘此卡之前的当次累计值；复核时再乘一次，每次分别四舍五入 |
| 不影响的内容 | 不乘本列或整船历史总分，不改变旧列账目 |
| 验证重点 | 加分前后卡序、逐步取整、倍率复核、历史总分保持 |

例：短箱本次50，先×1.5得到75，紧跟复核再×1.5得到113，而不是对整局分数乘倍率。

### 9. 复核奖励

| 字段 | 内容 |
|---|---|
| ID | `review` |
| 玩家说明要点 | 左侧相邻工单本次适用的计分效果额外执行一次，不额外成长 |
| 参数位置 | 无独立固定奖励；复制左邻本次产生的加分值或倍率 |
| 获取条件 | 已有可复核的计分工单，才有资格进入候选；当前正常流程只在第二阶段获得 |
| 局内状态 | 无独立成长，不增加原卡的接力档位、交付数或封顶标记 |
| 左邻有效 | 优先提货、长期客户、长短接力、边角专家、封顶交付、追加报酬、加急奖金；原条件必须成立 |
| 左邻无效 | 自己在最左侧、左边是转色协议、左边是复核奖励，或者左邻本次没有适用效果 |
| 不能做的事 | 不重放整条结算，不新增落箱事件，不产生复核套复核的无限循环 |
| 验证重点 | 只认紧邻、条件不成立时不加分、成长一次、倍率再乘、封顶标记一次 |

例：长期客户本次奖励70，复核再给70；原卡下一次奖励只从70变75，不会变80。

## 当前参数快照

| 配置项 | 当前值 | 影响范围 |
|---|---:|---|
| `basePerHalf` | 50 | 短箱50、长箱100，也参与封顶追加 |
| `samePerHalf` | 25 | 正下方每处同色半格接触，包括转色互认 |
| `orders.priority` | 20 | 两家货主的优先提货共用 |
| `orders.clientStart` | 20 | 两家长期客户的初始奖励 |
| `orders.clientGrowth` | 5 | 每次匹配交付的成长 |
| `orders.relayStep` | 10 | 每档接力增量 |
| `orders.corner` | 60 | 短箱补齐奖励 |
| `orders.flat` | 25 | 固定追加报酬 |
| `orders.rush` | 1.5 | 加急与复核加急引用的倍率 |
| `goals` | 2600／3000 | 两个阶段独立达标，不合并抵扣 |
| `highScoreGoal` | 8000 | 两阶段都通过后，按整船总分评高分交付 |

没有满列额外奖励。无工单单阶段最高2400，低于两个目标。以上值是当前原型参数，不是已经完成真人平衡验证的最终值。

## 实现、测试与待观察项

| 项目 | 当前记录 |
|---|---|
| 16张工单效果与局内状态 | 已实现 |
| 工单规则自动回归 | `check-orders.cjs`：16张、240种有序双卡组合、100种子的两次三选一与跨阶段规则 |
| 新门槛与候选自动回归 | `check-difficulty.cjs`：200种子的起手限制、边角＋转色限制、可行转色保留、基础上限与独立门槛 |
| 表现与交互 | 原型支持三选一、详情、拖动／按钮排序、逐卡触发、上次效果和局末JSON记录 |
| 真人体验验收 | 待逐项试玩；程序回归通过不代表每张卡都同样有趣或强度相等 |
| 当前平衡观察 | 优先提货、成长与倍率收益可能差异较大；边角专家通关余量较窄，需结合真实记录观察 |
| 候选算法边界 | 只做当前明确无解情况的筛选，没有通用求解器，也不保证每局每种策略都能通关 |

自动回归包括正常候选不提供的组合，用于检查底层规则。不能因为某组合通过效果测试，就宣称玩家能正常抽到它或该组合一定能达标。

## 日常修改流程

1. **提出变更**：明确改哪张ID、解决什么问题、改规则还是只改数值。未确认的想法先记为“提议”，不写成已确认规则。
2. **更新实现**：数值改 `config.js`；效果、配对或候选条件改 `orders.js`。玩家文案随参数更新，避免数值与文案不一致。
3. **同步管理表**：更新总表、对应详情、参数快照及下方历史；区分用户确认与原型临时调整。
4. **验证**：规则改动核对相应测试；影响收益或门槛时重新跑难度检查及策略模拟，写明局限。不因文档排版修改重跑全部游戏测试。
5. **试玩对照**：结算导出记录，保留种子、版本、工单顺序、逐阶段得分、放行数与操作反馈。

现阶段增加或停用工单需要改代码；下表不提供尚未实现的后台能力。局内JSON记录是一次对局的事实记录，本管理表是工单规则的设计记录，两者用途不同。
